# Auto Agree v1.0.0 — Reconstructed Historical Record

> Evidence class: **reconstructed from the original v1 commit** `37377373507d5fd8a4eb8712a47ce06e15927d4f`.
>
> v1 did not have a contemporaneous standalone verification report. This document records what the committed implementation actually did, and separately labels limitations that became visible in later versions. It does not invent benchmark numbers or tests that were not recorded at the time.

## 1. Purpose and initial architecture

v1 established the first cross-site Auto Agree implementation as a Manifest V3 static content script loaded on all matching HTTP(S)-style pages/frames.

The runtime model was a single `content.js` with four responsibilities in one layer:

1. discover checkbox-like controls;
2. extract nearby legal/auth text;
3. score whether the control was a mandatory agreement;
4. click the control and optionally retry.

The manifest used an all-site content-script match and `all_frames: true`, with `match_about_blank: true`. There was no service worker, storage layer, telemetry, server, or remote configuration path.

## 2. Candidate-first discovery

The first discovery model started from known checkbox shapes and then asked whether the nearby text looked like legal consent.

Recognized control shapes included:

- native `input[type="checkbox"]`;
- `role="checkbox"`;
- explicit `aria-checked` / `data-state` states;
- Ant Design, Element, Vant, Naive UI, Arco, Semi, TDesign-style checkbox wrappers;
- generic class names containing `checkbox`.

This established the original invariant that Auto Agree should not click arbitrary elements merely because agreement words exist somewhere on the page.

## 3. Semantic scoring

v1 used a weighted positive score rather than one boolean keyword.

Evidence included:

- Chinese “read/know + agree/accept” patterns;
- User/Service/License Agreement vocabulary;
- Privacy Policy / Privacy Agreement vocabulary;
- English Terms / Privacy / EULA / agreement wording;
- `required` / `aria-required` state;
- mandatory/required wording;
- login/register/phone/OTP context;
- nearby legal links.

The score threshold was `8`.

The first explicit negative vocabulary already excluded several categories that should not be treated as routine login friction:

- CAPTCHA / human verification;
- marketing, promotions and newsletters;
- auto-renewal / recurring subscription consent;
- remember-me / keep-signed-in;
- donation/tip/warranty/insurance wording;
- contacts, precision location, personalized advertising and third-party sharing.

This was the origin of the project’s later principle that **false positives cost more than false negatives**.

## 4. Context model

The candidate’s surrounding context was built from:

- document title;
- current pathname;
- the nearest form/dialog/login/register/auth-like ancestor.

Authentication vocabulary added score but was not by itself click authority.

A final pointer-down hook on Login/Register-like buttons triggered one last document scan before the user attempted to proceed. The extension still did not press Login/Register itself.

## 5. State and visibility handling

v1 attempted to recognize checked state through:

- native `input.checked`;
- `aria-checked=true`;
- `data-state=checked`;
- known checked CSS classes.

Visibility used `getComputedStyle()` plus `getBoundingClientRect()`.

The version also tracked click attempts with a `WeakMap`, preventing unlimited repeated clicks on the same target.

## 6. Dynamic DOM and Shadow DOM

A `MutationObserver` watched the document and discovered newly inserted controls.

v1 also searched for open Shadow Roots by walking every descendant with `querySelectorAll('*')` and observing any `element.shadowRoot` it encountered.

This provided basic Web Component coverage but had an important complexity cost: finding Shadow Roots was proportional to whole-subtree element count.

Closed Shadow Roots were not covered by this mechanism.

## 7. v1 retry behavior

After the first click, v1 scheduled one delayed retry after 500 ms if its own `checked()` function still reported false.

The intent was to tolerate frameworks that attach handlers shortly after insertion.

However, this introduced the most important correctness defect of v1:

- if a custom component **did become checked**;
- but v1 did not understand that component’s checked-state representation;
- then `checked()` returned false;
- and the retry could toggle the component back off.

This failure mode was explicitly corrected in v1.1.

## 8. Main v1 limitations later demonstrated

These are **retrospective limitations**, not claims that v1 had already measured them at release time.

### 8.1 Checkbox-first blind spot

If a website displayed a small classless visual box next to agreement text but exposed no checkbox/role/class semantics, v1 never created a candidate in the first place.

This is the exact architectural class later fixed by v1.1’s text-to-control reverse discovery and the real TRAE classless agreement case.

### 8.2 Blind retry toggle

Unknown custom checked state could cause successful activation to be undone by the delayed retry.

### 8.3 Whole-subtree Shadow discovery

`querySelectorAll('*')` was simple but scales with DOM size and became unacceptable for a permanent all-site extension.

### 8.4 Unbounded ancestor text construction

v1 used `innerText` / `textContent` on candidate ancestors before truncating the resulting string. Large subtrees could therefore allocate/process much more text than the final output limit suggested.

### 8.5 Layout-heavy visibility checks

`getComputedStyle()` and geometry reads occurred in ordinary candidate evaluation, which could force style/layout work after DOM mutation.

### 8.6 Single-layer architecture

Every matching frame received the full decision engine even when the page had no login or agreement UI.

Later versions progressively split this into Probe → Gate → Engine and lazy risk semantics.

## 9. Historical significance

v1 established the project’s durable core ideas:

- cross-site operation;
- semantic evidence rather than clicking every checkbox;
- explicit negative categories;
- login/auth context as supporting evidence;
- dynamic DOM observation;
- Shadow DOM awareness;
- idempotence attempts;
- no automatic Login/Register submission.

Almost every later version can be understood as making one of those ideas more precise, more bounded, or less error-prone.
