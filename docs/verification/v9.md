# Auto Agree v9.0.0 — Verification Report

Generated: 2026-08-08

## Scope

v9 is an invariant-recovery release derived by reconciling the complete v1→v8 engineering record against the live v8 runtime. It targets cases where historical safety/ownership requirements were only partially preserved in v8, plus Worker identity and cross-version dependency boundaries exposed by the same adversarial audit.

## Recovered invariants

- UNKNOWN-state classless controls are one-shot for the lifetime of the unresolved DOM element; cooldown expiry alone can never authorize a second toggle. If `HTMLElement.click()` itself fails before an action is dispatched, the one-shot is not consumed.
- Native `indeterminate`, `aria-checked="mixed"`, and data `indeterminate` / `mixed` states are tri-state or aggregate ambiguity and are not auto-confirmable.
- Gate→Engine seed handoff is consumed from the global exactly once but remains weakly readable by both Shadow bootstrap and scoped Engine bootstrap.
- Gate/Engine sentinels are published only after their dependencies are valid, so a partial or out-of-order injection cannot permanently poison later retries.
- Engine injection includes the current semantic core, and shared semantic/risk globals may refresh across extension versions while already-running old closures keep their captured prior objects.
- Profile storage origin is derived from Chrome `MessageSender.origin` / `url`; content-provided origin text is neither sent nor trusted. Profile operations fail closed when no usable HTTP(S) sender origin exists.

## New regression gates

### Tri-state refusal

Real unpacked Chrome now covers three independent ambiguous-state representations in the same routine login context:

- ARIA `aria-checked="mixed"`;
- custom `data-state="indeterminate"`;
- native checkbox `indeterminate === true`.

All three must remain untouched with an exact click count of zero.

### UNKNOWN one-shot

A classless visual control with no observable checked contract is allowed one activation. The fixture then waits beyond the normal 2.2-second click cooldown, changes its legal text to trigger fresh semantic work, and requires the click count to remain exactly one.

### Cross-version update modes

The v8→v9 real-browser update gate keeps two already-open pages alive across the same unpacked-extension replacement:

1. **dormant v8 Probe page** — no Engine exists before update; after new evidence appears, the old Probe hands off through the v9 Worker and the isolated-world sentinels must show a v9 Engine and no v8 Engine;
2. **already-active v8 Engine page** — v8 Engine is proven active before update; after update and a fresh dynamic agreement, that old Engine must remain the sole click authority, click exactly once, and no competing v9 Engine may appear in the document.

Both pages carry main-world markers that must survive the extension update, proving the pages themselves were not reloaded.

### Worker identity boundary

Deterministic Worker contracts prove that:

- a spoofed `message.origin` cannot redirect a profile write away from the Chrome-provided sender origin;
- a profile request without a usable sender origin fails closed with `missing-profile-origin`;
- Engine activation injects `semantic-core.js`, `risk-core.js`, and `engine.js` as one current-version dependency closure.

Static contracts additionally pin tier sentinel ordering, weak seed reuse, mixed-state handling, durable one-shot state, and the absence of content-side self-reported profile origin.

## Remaining boundary

An already-open page whose full older Engine tier was activated before an extension update may continue running that old closure until the page lifecycle naturally replaces it. v9 deliberately preserves this single-authority behavior instead of injecting a second Engine. A future live-tier replacement protocol would require an explicit cooperative teardown contract installed by the prior version; it cannot be retroactively imposed on v8 closures without risking duplicate click authorities.
