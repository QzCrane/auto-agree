# Auto Agree v8.0.0 — Verification Report

Generated: 2026-08-08

## Scope

v8 closes the largest remaining verification gap from v7: the release candidate is now loaded as a **real unpacked Manifest V3 extension** in Chrome for Testing, with the actual service worker, dynamic `chrome.scripting` injections, isolated worlds, frame handling, closed-Shadow extension API path and extension update lifecycle under test.

Runtime work hardens MV3 worker death/update behavior, sender lifecycle authority, scheduling fairness, native validation causality and cross-tier DOM ownership. A final profile-driven optimization also removes broad nearby-text extraction from the Probe's ordinary-checkbox hot path.

## Production changes

### Worker document lifecycle gate

Explicit non-active `MessageSender.documentLifecycle` states (`prerender`, `cached`, `pending_deletion`) are rejected before profile mutation or dynamic script injection. Probe/Gate/Engine lifecycle guards remain in place, giving the system a second independent lifecycle boundary in the worker.

### Restart-safe handoff

Probe→Gate and Gate→Engine messages have bounded retry delays after a runtime-channel failure. Profile GET/PUT/invalidation messages are replayed only through idempotent Worker operations. Persistent profile authority remains in `chrome.storage`; worker globals are treated as disposable caches/scheduling state rather than durable truth.

### Update rehydration

`runtime.onInstalled(reason=update)` records a session rehydration marker and performs a bounded bootstrap sweep across existing tabs/frames. A worker restarted before completion sees the marker and resumes. No `tabs` permission is added.

### Fair/stale-aware injection scheduler

The 4-global/2-per-tab hard execution limits remain. v8 adds:

- bounded queue aging so Gate work cannot starve behind a continuous Engine stream;
- per-tab tie rotation;
- 15-second stale-job expiry;
- hard queue cap 64;
- priority admission allowing a new Engine request to evict a younger queued lower-priority Gate job instead of failing behind low-value backlog.

### Native validity causality

A disabled proceed action contributes agreement-gating evidence only when credential controls are both non-empty and natively valid. `ValidityState.valid` / `willValidate` are read without calling `checkValidity()`, so malformed non-empty email/pattern inputs no longer make a disabled button look like evidence that Terms is the blocker.

### Weak handoff seed ownership

Cross-tier seed elements are carried through `WeakRef` and consumed/cleared by the next tier. v8 Gate/Engine still understand the old v7 strong `.seed` field solely for an in-place v7→v8 update transition.

### Profile-driven Probe optimization

The first real CPU profile showed Probe `onMutations`, `scan`, `directText` and deep scheduling near the top of the 5,000-checkbox workload. The main cause was semantic text extraction around every ordinary checkbox.

v8 changes that direction:

- ordinary checkbox-like nodes no longer perform a local bounded-text walk merely because they are checkboxes;
- ordinary controls inspect only their own hints plus explicitly referenced `aria-labelledby` / `aria-describedby` semantics;
- legal text discovery performs the reverse lookup to a nearby semantic control/container;
- external `label[for]` relationships remain supported on the rare legal-text path.

This makes Probe work closer to the number of meaningful legal-text candidates instead of the number of unrelated checkboxes.

## Real defect discovered only by unpacked E2E

The first true browser run exposed a production defect that all prior shim-level tests had missed.

After v7 extracted consequential-consent rules into `risk-core.js`, the classless reverse-discovery path in `engine.js` still contained stale bare references to the old private identifiers:

- `CONSEQUENTIAL_LOCAL`;
- `consequentialRisk`.

Native checkbox paths did not execute those statements, so standard positive/negative tests passed. The TRAE-derived classless path did execute them and threw a real `ReferenceError` before `performClick()`.

The repair routes those decisions through the public risk-core severity API (`severityFor(...)` / `SEVERITY.CONSEQUENTIAL`) and adds a static contract forbidding the stale identifiers in Engine source.

This failure is the strongest evidence for making real unpacked-extension E2E a permanent release gate: the defect was not a selector edge case but a module-boundary integration error invisible to the earlier in-page harness.

## Performance profiling

Workload: **5,000 unrelated checkbox labels followed by one real login agreement**, running the final unpacked extension in real Chrome while DevTools CPU profiling is active.

Before the profile-driven Probe optimization, a successful real run measured approximately:

```text
latencyMs:    330.9
taskDuration: 0.3056 s
CPU samples:  306
```

After the optimization, run 31248922179 measured:

```text
latencyMs:    286.1
taskDuration: 0.2662 s
CPU samples:  244
```

Relative movement for this synthetic real-extension workload:

- wall latency: **~13.5% lower**;
- TaskDuration: **~12.9% lower**;
- sampled CPU points: **~20.3% fewer**.

More importantly, Probe `directText` / broad checkbox-adjacent scanning dropped out of the top sampled hot functions. The remaining extension-heavy samples are primarily Engine work such as Shadow probing, fragmented-agreement checks and bounded traversal after the frame has already earned full-engine activation.

The release gate is tightened from the exploratory 4-second ceiling to:

- `latency < 1000 ms`;
- `TaskDuration < 0.8 s`.

These ceilings are intentionally much wider than the current ~286 ms / ~0.266 s observation to avoid turning GitHub-runner noise into flaky CI while still detecting multi-fold regressions.

## E2E harness calibration history

Several pre-behavior failures during construction of the release gate were harness failures, not AutoAgree runtime failures. They are worth retaining as test-engineering context:

- the runner's branded system Chrome did not load the unpacked extension through the chosen Puppeteer path;
- Puppeteer package installation with scripts suppressed requires an explicit `npx puppeteer browsers install chrome` step;
- path-based `enableExtensions` requires `pipe: true`;
- headed Chrome in CI requires Xvfb and foreground activation to match AutoAgree's intentional hidden-page quiescence;
- extension update verification must read the new runtime/worker state rather than trust stale client metadata.

The permanent CI workflow incorporates these constraints so future releases do not rediscover them.

## Remaining evidence boundary

v8 closes the **real unpacked extension** boundary for the committed regression corpus. It does **not** claim that the GitHub runner has logged into arbitrary production websites or that the current corpus proves zero false positives/false negatives across the internet.

Future real-site failures should be minimized, de-identified and added to the regression corpus. Current hard browser boundaries such as Chrome-owned UI, controls requiring trusted physical input, or purely Canvas/WebGL interaction without a usable DOM/accessibility surface remain outside the authority of this content-script architecture.
